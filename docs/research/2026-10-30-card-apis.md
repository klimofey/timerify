## 1. Shipping and registering the card from the integration

- **Static file.** `hass.http.async_register_static_paths([StaticPathConfig(url_path, path,
  cache_headers=True)])`: dataclass `HA/components/http/server.py:77-82`, method `:367-376`,
  directory-or-file resolution `:355-365`. `StaticPathConfig` is re-exported at
  `HA/components/http/__init__.py:62`. The old synchronous `register_static_path` is removed
  (blog: `https://developers.home-assistant.io/blog/2024/06/18/async_register_static_paths/`).
  - Cache headers: `HA/components/http/static.py:13-15`: 31 days, `Cache-Control: public,
    max-age=2678400`.
  - **[probe]** The file is served **without authentication**, with `ETag`, `Last-Modified` and a
    `304` on `If-None-Match`. `HEAD` returns 405 (use `GET`). The query string is ignored by
    routing, so `?v=...` busts the cache only on the client side.
  - **[probe]** Registering the same URL twice raises `RuntimeError('Added route will never be
    executed, method GET is already registered')`. So the registration belongs in `async_setup`
    (once per HA run), never in `async_setup_entry` (once per target, and again on every reload).
    HACS carries the same comment: "static paths can't be registered again when the entry reloads"
    (`hacs/integration`, `custom_components/hacs/frontend.py`).
- **Loading it on every dashboard: `frontend.add_extra_js_url(hass, url, es5=False)`**
  (`HA/components/frontend/__init__.py:427-433`; `remove_extra_js_url` at `:436`).
  - A plain function whose docstring says it lets custom integrations register an extra js module.
    No core integration calls it (grep of `HA/components/` finds only `frontend` itself); the
    users are HACS and `thomasloven/hass-browser_mod` (`custom_components/browser_mod/mod_view.py`).
  - It needs `hass.data[DATA_EXTRA_MODULE_URL]` (`:67`, created at `:650` in the frontend's own
    setup), so calling it before `frontend` is set up raises `KeyError`.
  - The index page lists the modules at `:869-910`; in safe mode the list is empty (`:892-895`). The
    template emits `import("{{ extra_module }}").catch(...)`
    (`home-assistant-frontend` `src/html/index.html.template:157-160`).
  - **[probe]** The served index HTML contained `import("/timerify_probe/probe-card.js?v=1")`. The
    module therefore loads at app boot, before any dashboard renders, for **every** dashboard,
    storage mode and YAML mode alike, with no user action.
  - **[probe]** At module-load time no `ha-*` element is defined, `window.customCards` is not yet an
    array and `window.loadCardHelpers` is undefined. At card `connectedCallback` time `ha-dialog`,
    `ha-card`, `ha-icon`, `ha-state-icon`, `ha-form`, `ha-relative-time` and `action-handler` are
    defined, `ha-md-dialog` is **not**, and `loadCardHelpers` is a function. So the module must
    not touch `ha-*` elements at top level.
  - `frontend/subscribe_extra_js` exists (`:1068`) but nothing in the frontend source consumes it.
- **Lovelace resource (the other route).** There is no public Python helper to add one.
  - `HA/components/lovelace/resources.py`: `ResourceStorageCollection` (create, update, delete over
    the admin WS commands `lovelace/resources/*`); `ResourceYAMLCollection` (`:27-45`) is read-only.
    `HA/components/lovelace/__init__.py:104-175` chooses between them by `resource_mode`;
    `lovelace.reload_resources` reloads the YAML ones.
  - **[probe]** `lovelace/info` returns `{"resource_mode": "storage"}` by default.
  - A user in YAML mode owns the resource list, so an integration cannot add to it
    (`DOCS/marketplace/guides/dashboard/`: in YAML mode the Marketplace cannot add the resource
    either; when a module is already loaded through `extra_module_url` it adds none).
  - Importing `homeassistant.components.lovelace` from a custom integration fails hassfest unless
    it is declared (below). browser_mod imports `ResourceStorageCollection` for exactly this.
  - Loading side: `FE/src/panels/lovelace/common/load-resources.ts:9-76`. Resources are not
    loaded in safe mode (`DOCS/frontend/custom-ui/resources/`, which also says to bust the cache
    with `?v=2`).
- **Documentation gap.** Neither `add_extra_js_url` nor `async_register_static_paths` is described
  in the contributor docs for cards (grep of `llms-full.txt`; the only mention is the Marketplace
  guide's `extra_module_url` sentence). They are stable in practice (used by HACS and browser_mod
  for years) but not a documented contract.
- **Cache-busting.** The 31-day cache means a new bundle is not seen without a changed URL. Use
  `add_extra_js_url(hass, f"{url}?v={key}")`; browser_mod does `url + "?" + version`
  (`StaticPathConfig(url, path, True)`). The key can be the manifest version or a content hash
  of the file (open question 5).
- **hassfest, run for real** (hassfest 2026.10.4 from a sparse clone of core `script/`):
  - The current integration passes.
  - **[probe]** `from homeassistant.components import frontend` needs **no** declaration:
    `frontend` is in the allow-list (`ALLOWED_USED_COMPONENTS`,
    `script/hassfest/dependencies.py`, about `:95-130`).
  - **[probe]** Importing `http` or `lovelace` fails with "Using component X but it's not in
    'dependencies' or 'after_dependencies'". Adding `http` to `after_dependencies` clears it.
  - Runtime: `hass.http` exists only when `http` is set up, and `add_extra_js_url` raises
    `KeyError` without `frontend`. `dependencies: ["http"]` is cheap (the frontend needs it
    anyway). Forcing `frontend` with `dependencies` would make a headless install load the whole
    UI stack; `after_dependencies: ["frontend"]` plus a guard
    (`"frontend" in hass.config.components`) avoids that (open question 4).
- **Where the bundle can live.** Everything HACS installs must be inside
  `custom_components/timerify/` (`DOCS/marketplace/reference/repository-structure/`), so the
  bundle goes in `custom_components/timerify/frontend/`. The smoke compose file already mounts
  `../../custom_components` read-only, so the container serves it without any new mount.

## 2. The custom card contract

Docs: `DOCS/frontend/custom-ui/card/`, `.../card-editor/`, `DOCS/frontend/reference/hass-object/`,
`DOCS/frontend/architecture/hass-and-contexts/`.

- **Element and registration.** A custom element named `timerify-card`, used as
  `type: custom:timerify-card`. `setConfig(config)` is required and must throw on an invalid
  config. The `hass` property setter is called on **every state change in the whole home**, so it
  has to be cheap. `getCardSize()` is in 50 px units (masonry). `getGridOptions()` serves sections
  (12 columns, 56 px rows, 8 px gaps; keys `columns`, `rows`, `min_columns`, `max_columns`,
  `min_rows`, `max_rows`). Types: `FE/src/panels/lovelace/types.ts:60-104` (`LovelaceGridOptions`,
  `LovelaceCard`, `LovelaceConfigForm`, `LovelaceCardConstructor`).
- **Picker entry.** `window.customCards = window.customCards || []; window.customCards.push({type,
  name, description, preview, documentationURL, getEntitySuggestion})`; `type` has no `custom:`
  prefix (`FE/src/data/lovelace_custom_cards.ts:21-31`). The frontend reuses an existing array
  (`:67-84`), so the push must not replace it.
  - Picker code: `FE/src/panels/lovelace/editor/card-editor/hui-card-picker.ts:420-437` (custom
    cards sorted; `showElement: ccard.preview`), `:579-591` (`_tryCreateCardElement` sets only
    `hass`), `:608-672` (the `custom:` prefix is added, and the stub config comes from
    `getCardStubConfig`).
  - `preview: true` shows a live card in the picker. The picker creates the element and sets
    only `hass`, so the card must render with `_config` from `getStubConfig`. The `preview`
    boolean is also set on the card while it is shown in the editor (docs).
  - `getEntitySuggestion` is read at `FE/src/panels/lovelace/card-suggestions/index.ts:31-43`.
  - **UNVERIFIED in a browser:** how the picker preview looks. Only the source was read.
- **Stub config.** `static getStubConfig(hass, entities, entitiesFallback)` (docs: `entities` =
  entities not yet used on the dashboard, `entitiesFallback` = used ones; both exclude unavailable
  and unknown). The result is merged with `{type}`
  (`FE/src/panels/lovelace/editor/get-card-stub-config.ts:5-25`). Only generic entity filtering
  is available, so filtering to Timerify's "Run for" numbers must be done by the card itself, from
  `hass.entities` (platform `timerify`, translation key `run_for`).
- **Editor.** `static getConfigElement()` (own editor element) wins over `static getConfigForm()`
  (a schema for the built-in `ha-form`); both are documented in `.../card-editor/`.
  `FE/src/panels/lovelace/editor/config-elements/hui-card-element-editor.ts:26-46`.
  - **[probe]** The frontend called `getConfigForm` of the probe card and rendered it.
  - `LovelaceConfigForm` = `{schema, assertConfig, computeLabel, computeHelper}`
    (`types.ts:60-104`). Schema types: `FE/src/components/ha-form/types.ts:5-130` (grid,
    expandable, optional_actions, constant, divider, string, `selector`; `visible` conditions).
  - Selectors, about 55 types (`FE/src/data/selector.ts:28-88`), including `entity` (with
    `domain` and `integration` filters), `entity_name`, `icon`, `number`, `boolean`, `select`,
    `object`, `ui_action`, `theme`, `duration`, `text`, `navigation`, `state`, `attribute`.
    `ha-form` is an internal element, but `getConfigForm` is the documented way to use it.
  - A schema form covers an entity, a layout select, an icon and a duration list. A list of
    presets with a custom UI, or an editor of per-interval options, would need `getConfigElement`.
- **Lookup timeout.** The frontend gives a not-yet-defined custom element 2 s before it shows an
  error card (`FE/src/panels/lovelace/create-element/create-element-base.ts:39, 173-202,
  318-349`). The extra module is imported at boot, so this normally holds; see the first-visit
  reload in section 6 for the one case where it did not.
- **Helpers.** `window.loadCardHelpers()` is defined at `FE/src/panels/lovelace/ha-panel-lovelace.ts:46`
  (`custom-card-helpers.ts:1-12`: `showAlertDialog`, `showConfirmationDialog`, `showPromptDialog`,
  `showEnterCodeDialog`, `importMoreInfoControl`, `createCardElement` and others).
- **Finding the timer's entities.** `hass.entities` is an `EntityRegistryDisplayEntry`
  (`FE/src/data/entity/entity_registry.ts:16-30`; backend `HA/helpers/entity_registry.py:309-345`).
  - **[probe]** Keys: `entity_id`, `device_id`, `area_id`, `next_name_part`, `labels`,
    `translation_key`, `platform`, `entity_category`, `has_entity_name`, `name`, `icon`, `hidden`,
    `display_precision`. There is **no** `unique_id` and **no** `config_entry_id`.
  - `hass.devices` is a `DeviceRegistryEntry` (`FE/src/data/device/device_registry.ts:25-50`).
    **[probe]** For a device Timerify made (a target without a device), `config_entries` and
    `primary_config_entry` are the Timerify entry. For a target that is on another integration's
    device (the demo switch), the device lists **only** the demo entry: Timerify's entities sit on
    it through `Entity.device_entry` without adding its entry (`custom_components/timerify/entity.py:12-59`).
  - So the siblings of a "Run for" number are found with `device_id` + `platform === "timerify"` +
    `translation_key` (`run_for`, `ends_at`, `next_command`, `interval`). That is ambiguous when two
    timers share one device (a multi-switch device with two targets).
  - The entry id (needed for the settings link and for any entry-scoped lookup) is **not** in the
    display registry or the device registry for a shared device. **[probe]** The WS command
    `config/entity_registry/get` returned `config_entry_id` and `unique_id`
    (`<entry_id>_run_for`). It is not admin-only (`HA/components/config/entity_registry.py:98-125`,
    no `@require_admin`); `config/device_registry/list` is also not admin-only
    (`HA/components/config/device_registry.py:56-100`). **UNVERIFIED** with a non-admin user at
    runtime (code read only).
  - The "Run for" number has no attribute naming its target. The controller snapshot has no start
    time or total duration, so a progress fill needs a new attribute (open questions 1 and 2).
- **Formatting helpers on `hass`.** `hass.formatEntityState(stateObj)` and
  `hass.formatEntityName(stateObj)` (`FE/src/types.ts:275-295`; docs reference). **[probe]**
  `formatEntityState` of "Run for" gave "19 min"; `formatEntityName` gave "Smoke boiler Run for".
  Timestamp sensors format as date plus time (`FE/src/common/entity/compute_state_display.ts:256-270`).

## 3. Interaction

- **Tap and hold.** The frontend's own handler is `action-handler`
  (`FE/src/panels/lovelace/common/directives/action-handler-directive.ts`): `holdTime = 500`
  (`:54`), `DOUBLE_CLICK_TIME = 250` (`:37`), a hold fires an `action` event with
  `{action: "hold"}` (`:259-260`), tap and double-tap at `:261-288`. It is a global `<action-handler>`
  element appended to `body` (`:331-341`). It is **not** part of `custom-card-helpers`, and the
  docs promise no `ha-*` element. **[probe]** `action-handler` is defined at card connect time.
  Whether a custom card may rely on it is **UNVERIFIED** (undocumented). A card that wants
  tap, hold and keyboard access writes its own pointer handling (pointerdown timer of 500 ms to
  match the frontend, `pointercancel`, a `button`-role element for keyboard users).
- **`ha-card`.** Styled by `--ha-card-background`, `--ha-card-border-radius`,
  `--ha-card-box-shadow`, `--ha-card-border-width`, `--ha-card-border-color`
  (`FE/src/components/ha-card.ts:10-72`). **[probe]** Defined at connect time. The docs say
  there is no public component library (`DOCS/frontend/custom-ui/`); `ha-card` is the one
  exception in practice, not on paper.
- **More-info.** Dispatch `hass-more-info` with `detail: {entityId}` from the card; it must be
  `bubbles` and `composed` (`FE/src/state/more-info-mixin.ts:19-71`; params type
  `MoreInfoDialogParams`, `FE/src/dialogs/more-info/ha-more-info-dialog.ts:97-107`).
  **[probe]** The click opened `ha-more-info-dialog`, the URL became
  `?more-info-entity-id=<id>&more-info-view=info`, `history.state` became
  `{dialog: "ha-more-info-dialog"}`, and Escape closed it and removed the query again. It is
  documented in the reference page; this is the supported way to open an entity's details.
- **A dialog of the card's own.** Two options, with what I verified:
  - **`show-dialog` event.** `detail: {dialogTag, dialogImport, dialogParams, addHistory?,
    parentElement?, dialogAnchor?}` (`FE/src/dialogs/make-dialog-manager.ts:35-42, 81-200,
    286-310`). The listener is on the `<home-assistant>` element (`dialog-manager-mixin.ts`). It
    creates `document.createElement(dialogTag)`, calls `showDialog(params)` (legacy element) or
    sets `params` (elements with `dialogNext = true`), appends it to the `<home-assistant>` shadow
    root, and pushes a history entry so Back closes it. **[probe]** A card-defined element worked:
    `showDialog({hello: "world"})` was called, the element sat in the `home-assistant` shadow
    root, `history.state` was `{dialog: "<tag>"}`, **Escape did not close it** (the dialog must
    handle keys itself), and history Back called its `closeDialog()` and removed it.
    It is described only in the contributor docs for frontend developers (`llms-full.txt`),
    so it is an internal, unversioned API for a custom card.
  - **Built-in dialogs of `loadCardHelpers()`** (alert, confirmation, prompt, enter code): in the
    helper file, usable for a stop confirmation; not for a pop-up with presets and a list.
  - `ha-dialog` is Web Awesome based and lazy-loaded (defined at connect time **[probe]**);
    `ha-md-dialog` does not exist at this tag (0 hits in `FE/src`); `ha-adaptive-dialog` and
    `ha-dialog-footer` exist in `FE/src/components/`. None is promised to custom cards.
  - A third option, **UNVERIFIED**: a native `<dialog>` with `showModal()` inside the card's own
    shadow DOM. It depends on no HA internals, and gives focus trap and Escape for free; Back
    button handling would be the card's own work.
- **Services and WS.** `hass.callService(domain, service, data, target, notifyOnError = true,
  returnResponse)` and `hass.callWS(msg)` (`FE/src/types.ts:240-255`; reference page). Timerify's
  services are entity services on `number` entities of integration `timerify`
  (`custom_components/timerify/services.yaml`): `add_time`, `run`, `add_command`,
  `cancel_command`; call them with `target: {entity_id: "number.<x>_run_for"}`. `add_command`
  supports `return_response`. With `notifyOnError` true the frontend itself shows a toast for a
  failed call, with the message looked up in the integration's `exceptions` translations by
  `err.translation_domain`, `translation_key` and `translation_placeholders`, and the generic
  "action failed" text otherwise (`FE/src/state/connection-mixin.ts:105-185`). So a translated
  `ServiceValidationError` from Timerify reaches the user without card code.
- **Navigation.** A card calls `history.pushState(null, "", path)` and then dispatches
  `new CustomEvent("location-changed", {detail: {replace: false}})` on `window`; this is what
  `navigate()` does (`FE/src/common/navigate.ts:194-251`, event at `:228-230`; the dialog stack is
  closed first, `:55-100`).
  - **[probe]** From the card, `/config/integrations/integration/timerify#config_entry=<entry_id>`
    changed the view **without a reload**, opened the Timerify integration page, and expanded and
    highlighted that target's row.
  - Code: `FE/src/panels/config/integrations/ha-config-integration-page.ts:163-165, 179, 903-920`
    (`_highlightEntry`); the `?domain=` redirect is in `ha-config-integrations.ts:195-205`. The
    device page is `/config/devices/device/<device_id>` (`ha-config-integration-page.ts:616`).
  - The config pages need an administrator. Hide the link when `hass.user.is_admin` is false
    (`FE/src/types.ts:105-112`). **[probe]** `hass.user.is_admin` is `true` for the smoke user.

## 4. Rendering

  `--secondary-text-color` (`:9`), `--primary-color` (`:15`), `--divider-color` (`:20`),

  (`semantic.globals.ts`). Custom properties inherit through shadow DOM, so a card only needs
  `var(--primary-text-color)` and friends; dark mode and user themes come for free.
- **Icons.** `<ha-icon icon="mdi:...">` (`@property icon`) and `<ha-state-icon .stateObj .hass>`
  (consumes Lit contexts, `FE/src/components/ha-state-icon.ts:24-110`). Both are internal. An entity
  icon comes from `icons.json` of the integration through `entityIcon`; Timerify's file has
  `mdi:timer-outline` for `run_for`, `mdi:clock-end` and `mdi:calendar-clock`.
- **HA's own timer card counts down in the browser.**
  - `FE/src/common/controllers/timer-remaining-time-controller.ts:15-70`: a
    `window.setInterval(..., 1000)` only while the state is `active`, re-rendering each second.
  - `FE/src/data/timer.ts:86-101`: `timerTimeRemaining` =
    `Math.max((finishes_at - new Date().getTime()) / 1000, 0)`. It uses the **browser clock** with
    no server offset, so a skewed client clock shows a skewed countdown. **UNVERIFIED** whether
    the frontend offers a server-time offset for this.
  - Display: `secondsToDuration` (`FE/src/common/datetime/seconds_to_duration.ts`: `H:MM:SS`,
    `M:SS` or `S`). `ha-timer-remaining-time` is an internal element.
  - A card with the same approach computes `ends_at - Date.now()` on a 1 s interval, started in
    `connectedCallback` and cleared in `disconnectedCallback`, only while "Ends at" is in the
    future; this meets the spec's "no sub-minute state writes".
- **Relative time.** `FE/src/common/datetime/relative_time.ts:5-26` uses a memoized
  `Intl.RelativeTimeFormat(locale.language, {numeric: "auto", style})`, with the unit chosen by
  `selectUnit` (`FE/src/common/util/select-unit.ts`). `ha-relative-time` (internal;
  `ha-relative-time.ts:51-89`) refreshes every 1 s when the difference is under 60 s and every 60 s
  otherwise. A card can call `Intl.RelativeTimeFormat` and `Intl.DateTimeFormat` itself with
  `hass.locale.language`, with no dependency on internals.
- **Locale and time zone.** `FrontendLocaleData`: `language`, `number_format`, `time_format`,
  `date_format`, `first_weekday`, `time_zone` (`"local"` or `"server"`) (`FE/src/data/translation.ts`).
  Frontend helpers: `resolve-time-zone.ts:23-26`, `format_time.ts:8-22`, `use_am_pm.ts:5-19`.
  **[probe]** `hass.locale` = `{language: "en", number_format: "language", time_format: "language",
  date_format: "language", time_zone: "local", first_weekday: "language"}`; `hass.language` = `"en"`;
  `hass.config.time_zone` = `"UTC"`; `hass.config.version` = `"2026.10.4"`. A card that prints a
  clock time must honour `locale.time_zone` (`"server"` means `hass.config.time_zone`) and the
  12/24-hour setting.

## 5. Localisation of the card (en and ru)

- **Runtime mechanism.** `hass.loadBackendTranslation(category, integrations)`
  (`FE/src/types.ts:237-241`; `FE/src/state/translations-mixin.ts:297-387, 442-486`) calls the WS
  command `frontend/get_translations` `{language, category, integration, config_flow}`
  (`FE/src/data/translation.ts`; backend `HA/components/frontend/__init__.py:1021-1044`).
  - Keys come back as `component.<domain>.<category>.<flattened path>`
    (`HA/helpers/translation.py:28-37, 280-300`); English is the fallback
    (`:218-246`). The TS `TranslationCategory` type lists `title`, `state`, `entity`,
    `entity_component`, `exceptions`, `config`, `config_subentries`, `config_panel`, `options`,
    `device_automation`, `mfa_setup`, `system_health`, `application_credentials`, `issues`,
    `preview_features`, `selector`, `services`, `triggers`, `conditions`. It has no `common`, but
    the backend accepts any string.
  - **[probe]** `await hass.loadBackendTranslation("common", "timerify")` returns a localize
    function; `l("component.timerify.common.card_stop")` gave "Stop", and a `{minutes}`
    placeholder was substituted (`l(key, {minutes: 5})` gave "5 min left"). `config_panel` with
    nested keys also loads. A missing key gives `""`. An unknown category returns
    `{resources: {}}`. The returned function is a new one, not `hass.localize`. A direct WS call
    with `language: "ru"` returned the Russian strings.
  - So the card gets its strings with one WS round trip per category, in the user's language,
    with the English fallback applied by the server. **UNVERIFIED:** a full browser run with
    `hass.language = "ru"` (only the WS call was run with `ru`).
- **Which top-level keys of `translations/<lang>.json` hassfest accepts for a custom integration**
  (`script/hassfest/translations.py`, `_gen_strings_schema`, about `:395-632`): `title`, `config`,
  `config_subentries`, `options`, `preview_features`, `selector`, `device_automation`,
  `system_health`, `config_panel`, `application_credentials`, `issues`, `entity_component`,
  `device`, `entity`, `exceptions`, `services`, `conditions`, `triggers`, `conversation`, `common`.
  - Only `translations/en.json` is validated for a custom integration
    (`validate_translation_file`, `:680-760`); other languages are not.
  - `common` is a flat `slug -> string` map (`:630-632`: `cv.slug` keys,
    `translation_value_validator` values). `config_panel` is a tree of any depth whose keys match
    `translation_key_validator` or `_` (about `:572-578`).
  - **[probe]** hassfest on a scratch copy: `common` with flat slug keys OK; `common` with a

  - Docs: `DOCS/core/integrations/translations/` list the sections, say a custom integration ships
    finished files with a complete `en.json`, and say references (`[%key:...%]`) do not work in
    custom files.
- **Options for the card's own strings** (button labels, "min left", empty states, errors):

  | Option | Valid for hassfest | Loadable at runtime | Trade-off |

  | A. `common` flat slug keys | yes | yes [probe] | Smallest; flat only, so keys are like `card_stop`; meant for in-file reuse, not for a card |

  | D. Strings in the bundle, or a JSON beside it | n/a | yes | Needs a Cyrillic exception for the Russian strings: the pre-commit allow-list covers only `translations/<lang>.json` (non-en), `sentences/<lang>/` and `README.ru.md`; escaped `\uXXXX` would pass the hook but defeats the rule's purpose |

## Recommendations

1. Register the file and the module in `async_setup`, once: a second registration raises
   `RuntimeError` and `async_setup_entry` runs per target.
2. Use `add_extra_js_url` (not a Lovelace resource): it loads on every dashboard in both modes
   and has no YAML-mode conflict or admin-only step.
3. Declare `http` in `dependencies`, `frontend` in `after_dependencies`, and guard the call
   with `"frontend" in hass.config.components`: hassfest requires the declaration and
   `add_extra_js_url` raises `KeyError` without the frontend.
4. Add `?v=<content hash or version>` to the module URL: the static path is cached for 31 days.
5. Configure the card with `entity:` of the "Run for" number: it is the one unambiguous handle
   (a target-based config breaks for a target without a device, and for two timers on one device).
6. Fetch `config_entry_id` once per card with `config/entity_registry/get` and cache it: the
   display registry and a shared device do not carry it.
7. Count down in the card from the "Ends at" timestamp on a 1 s timer that runs only while a timer
   is active, as HA's timer card does, and format times with `Intl` and `hass.locale`.
8. Write the tap and hold handling in the card (500 ms hold, pointer events, keyboard
   operable): `action-handler` is undocumented, and `custom-card-helpers` does not ship it.
9. Open the entity details with `hass-more-info`; it is the documented route and was verified.
10. Navigate to `/config/integrations/integration/timerify#config_entry=<id>` with `pushState` plus
    `location-changed`, shown only when `hass.user.is_admin`: verified to highlight the row.
11. Use `getConfigForm` for the editor first (documented, `ha-form` selectors), and a
    `getConfigElement` only if the presets list needs it: less custom UI to maintain.
12. Load strings with `loadBackendTranslation` from a hassfest-valid category (open question 3):
    it needs no new endpoint and keeps Cyrillic in `translations/ru.json`.
13. Use `static properties` and `static styles` in Lit: no decorator or compiler-option
    dependency.
14. Build with one bundler and one config (esbuild or rollup, open question 5), type-check with
    `tsc --noEmit`: the bundler does not type-check.
15. Run card E2E with Playwright in a separate invocation from `pytest`, after a login, service
    worker and reload priming step: the first-visit reload breaks naive tests.
16. Factor `scripts/smoke/run.py` helpers into an importable module before adding the card E2E:
    one onboarding and compose path instead of two.

## Open questions needing a ruling

1. **How the card finds a timer.** `entity:` of the "Run for" number is unambiguous, but the card
   still needs the entry id and the target. Should the integration expose them (an attribute on
   the number: `target_entity_id`, `entry_id`), or is `config/entity_registry/get` plus
   `device_id` siblings acceptable? Without an attribute, two timers on one device cannot be told
   apart by device alone.
2. **Progress fill.** The controller snapshot has no start time or total duration, so a progress
   bar cannot be drawn exactly. Add a `started_at` or `duration` attribute (or state) to the
   "Ends at" sensor or the number, or draw no progress?
3. **Card strings.** `common` flat slugs (A), a `config_panel` tree (B), or bundle strings with a
   Cyrillic path exception to repository rule 1 and the pre-commit allow-list (D)?
4. **Manifest dependencies.** `dependencies: ["http"]` with `after_dependencies: ["frontend"]` and
   a guard, or a hard `dependencies: ["frontend", "http"]` (forces the UI stack on a headless
   install)?
5. **Bundle delivery and cache key.** Commit the built `custom_components/timerify/frontend/*.js`,
   or build it at release and ship a `zip_release` (HACS `hacs.json` `zip_release`/`filename`)?
   Cache key: manifest version (stale during development) or content hash (computed in an executor
   job at startup)? Bundler: esbuild (one dependency) or rollup (browser_mod precedent)?
6. **E2E runner.** Python `pytest-playwright` (reuses the harness, separate session) or Node
   `@playwright/test` (first-class runner, trace viewer, same toolchain as the card tests) with
   the Python harness only starting and onboarding HA? And may `scripts/smoke` helpers be moved
   into a shared module with a configurable port?
7. **Pop-up technique.** The frontend's `show-dialog` (verified here, but internal and
   unversioned) or a native `<dialog>` in the card's shadow DOM (no HA dependency, **UNVERIFIED**
   in HA)? This also decides whether Back and Escape close it.
8. **TypeScript version.** 7.0.2 (latest) or 6.0.3 (what the HA frontend builds with)?
9. **Admin-only link.** A non-admin user cannot open the settings page; hide the link (the spec
   says "link to settings") or show it disabled?

# Timerify 1.1.0: the issue wave and the owner's new features

Date: 2026-11-01. Owner: klimofey.

This spec extends `docs/superpowers/specs/2026-10-28-timerify-design.md`, called "the base
spec" here. Where it is silent, `RULINGS.md` applies, then this document.

- **The owner's decisions:** recorded in `.superpowers/issue-triage-1.1.0.md`. They are binding
  and are restated here where a part needs them.
- **Issues:** every issue named below has a body on GitHub with its "Where" and its "Fix". The
  plans read those bodies, which this spec does not repeat.

## Why

1.0.0 shipped with 25 known issues, triaged into GitHub issues #7 to #31. Since then the owner has
used it and asked for seven more things (#35 to #41). 1.1.0 fixes everything that can be fixed
cleanly. Whatever waits on Home Assistant itself is labelled `upstream`, with a comment saying
what it waits for.

## Goals

The wave is split into five parts. Each part is one branch, one plan and one PR, merged in this
order. Each part is independent of the parts after it.

### Part A: engine and reliability

- **#31: test harness.** A FakeTarget dispatches each call to the fake that owns the entity. A
  call for an entity no fake owns fails loudly. This lands first in the part, because the other
  fixes test two targets of one domain.
- **#11:** bound re-sends and the give-up warning per wish, as the issue says.
- **#12:** before Home Assistant has started, commands record and save, and fold nothing.
- **#13:** what came due while the target was unavailable is logged on start-up and on target
  reports too.
- **#18:** the capability filter applies when a change is carried out, for commands and windows
  alike. There is one warning per dropped setting.
- **#10:** a target entity that was deleted creates a Repairs issue: "The device of timer X was
  deleted". Its fix flow deletes the timer.
  - Until the user acts, the timer does nothing and says so in the issue.
  - Restoring the entity (same entity id) clears the issue, and the timer works again.
  - It is checked at set-up and live, through `source_entity_removed`.
- **#17:** a stored timer that fails validation (`stored_timer_invalid`) creates a Repairs issue.
  Its fix flow "Reset the stored timer" keeps the entry and its intervals, drops the store, and
  reloads the entry.
- **#14:** look in the 2026.11 sources for a signal that fires when "Reload core configuration"
  changes the time zone.
  - If there is one, follow it.
  - If not, label the issue `upstream` and comment. No local workaround.

### Part B: timer and interval forms, entities

- **#35: per-timer maximum of Run for.**
  - A field "Maximum of Run for" (minutes, 1 to 1440, default 1440) goes on the first form of a
    new timer and on the first form of its settings.
  - It sets the `number` entity's maximum, so the slider and the card's controls built on it
    follow it.
  - The default duration must not be larger than the maximum. The form says so as a field
    error.
  - Ruling: the maximum is a limit of the slider, not of the timer.
    - Actions, voice, pending commands and schedule windows keep the global 1440-minute limit.
    - A countdown longer than the maximum, started by those paths, runs in full. The number
      shows its minutes left, which may then be above the slider's end.
    - Why: the owner asked for a usable slider ("I rarely set more than two hours"). Refusing a
      schedule window or a spoken "for 3 hours" would change behaviour the base spec defines.
- **#37: button entity.**
  - A checkbox "Turn off button" goes on the first form of a new timer and of its settings,
    default off.
  - When it is ticked, a `button` entity "Turn off" sits on the timer's device.
  - Pressing it is the existing stop command. So it turns off a Loose device that runs without a
    countdown too.
  - Pin with a test that Run for set to 0 by hand turns a running device off in Loose mode
    (base spec R2), if no test does yet.
- **#16:** editing an interval keeps a stored setting that the target no longer offers.
  - It is saved untouched.
  - While the target does not offer it, a Repairs issue names the interval and the setting. The
    issue is a warning, with no fix flow, like the ones Spook creates.
  - The issue clears when the target offers the setting again, or the interval no longer holds
    it.
  - When the window runs, the setting is skipped with a log warning (#18).
- **#15:** a generated interval title is marked as generated in the subentry data. An edit
  regenerates it while the mark is set, in the current language.
  - Existing subentries are migrated: the mark is set when the title equals the one generated
    from the data in any shipped language.
- **#40: the integration page not re-rendering.**
  - Reproduce the bug on 2026.10.4 and on 2026.11.0b1 or later.
  - If Timerify causes it (how or when entries and subentries are updated or reloaded), fix it.
  - If it is Home Assistant's frontend, label the issue `upstream`, with the exact steps and
    versions in a comment. Reporting it upstream needs the owner's consent.

### Part C: automations

- **#38: device actions** in the Device block of the automation editor, on the target's device
  (or the fallback device): "Run for N minutes", "Add N minutes", "Stop". Each calls the same
  core path as the actions `timerify.run`, `timerify.add_time` and stop. Strings are in
  en and ru.
- **#39: device triggers:**
  - "A countdown started";
  - "A countdown ended" (by expiry, stop or a manual off);
  - "A pending command came due".

  They are built on Timerify's own events or entity states, whichever the public device-trigger
  API supports cleanly. The plan verifies this in `.venv`. Strings are in en and ru.

### Part D: voice

- **#26:** "for 1 hour 30" is 90 minutes for devices without a temperature, in en and ru.
- **#29:** delays above 100 minutes or 100 hours are understood, up to the command limits. A delay
  above a limit is refused, naming the limit.
- **#19:** commands at a clock time ("turn on the boiler at 7:30", "tomorrow at 7"), in en and ru.
- **#22:** spoken forms of generated interval titles ("the 6:30 schedule").
- **#23:** a name with the Russian letter yo is matched when said with ye. One folding, in one
  place, for names, titles and modes.
- **#24:** Russian words for fan, preset and humidifier modes come from Home Assistant's entity
  translations for the house language, when they exist. The raw value stays as an alternative.
- **#25:** HVAC mode words are scoped per distinct set of modes, not the union over timers.
- **#20:** a target without a registry entry that changes its friendly name or its mode list
  rewrites the voice file. It is rewritten only when the written names or modes differ.
- **#21:** add the phrasings found so far.
  - Look in the 2026.11 sources for a way to keep a custom intent's names out of core's
    fallback. Use it if there is one.
  - Otherwise label the issue `upstream` and comment.
- **#27:** a hook exception for `tests/fixtures/ru/`, with its test. Fixtures hold the rendered
  Russian answers per count class, and a test compares them.

### Part E: the card

- **#30:** the server serves the card bundle it registered at start-up, until it restarts.
  - Keep the bytes read at registration, and serve them at the hashed URL instead of the file
    on disk.
  - A HACS or Marketplace update then changes the card only together with the server.
- **#36:** the tap, double tap and hold actions are configurable on both layouts, in the card
  editor.
  - Timerify's choices: open the pop-up, run for the default duration, stop.
  - Home Assistant's standard choices: more info, toggle, navigate, perform action, none.
  - Defaults keep today's behaviour: tap opens the pop-up; hold on the round layout does what it
    does today; double tap does nothing.
- **#37: card option.**
  - "Show a Turn off button" makes the card and its pop-up show a Turn off button while the
    target is on, with a countdown or without.
  - It is the stop command.
- **#41: Mushroom style.**
  - A card option "Mushroom style", default off, so a card that does not turn it on looks as
    it does today.
  - When it is on and Mushroom's cards are defined in the browser, the card reads Mushroom's
    theme variables (`--mush-*`), each falling back to Mushroom's own default. A theme that sets
    them changes the card too.
  - When Mushroom is not defined, the card keeps the Home Assistant look, and the editor says
    Mushroom was not found.
  - Only the variable names are shared; no Mushroom code is copied.
- **#8:** the card corrects the countdown by the server's clock. `timerify/timer` returns the
  server's time, and the card keeps the offset measured at lookup.
- **#9:** look in the 2026.11 frontend for a way to translate the option labels of a card's
  config form.
  - If there is one, use it.
  - If not, label the issue `upstream` and comment.
- **#28:** pin happy-dom 21.0.4, on or after 2026-11-03. If the card part ends earlier, this is a
  small PR of its own on that date.

### Release

- **#7:** the minimum stays 2026.10.4. If 2026.11.0 is out by the release, run E2E and the smoke
  test against it as well, and report the result. #7 stays open, with a comment, until the
  owner raises the minimum.
- **Version:** 1.1.0 in `manifest.json`, `pyproject.toml` and `uv.lock`.
- **Checks:** the full gate on main, and a manual smoke test with screenshots of the new
  features.
- **Release:** draft release notes. The owner approves the GitHub Release before it is
  published.

## Non-goals

- No change to rules the base spec defines, unless an issue above changes them on purpose.
- Raising the minimum Home Assistant version (#7).
- New languages.

## Constraints

Everything in `CLAUDE.md` applies.

- **Testing:**
  - Only public Home Assistant APIs, checked in `.venv`.
  - Tests are user scenarios with frozen time.
  - No sleeps or polling.
- **Documentation:**
  - Every user-visible change updates `docs/en` and `docs/ru` in the same commit.
  - New strings go in `translations/en.json` and `ru.json`.
  - Russian Home Assistant screen names come from `.superpowers/ui-names/ui-term.py`.
- **Issues:**
  - Every part's PR closes the issues it fixes ("Closes #N").
  - An issue left open gets the label `upstream` and a comment saying what it waits for.

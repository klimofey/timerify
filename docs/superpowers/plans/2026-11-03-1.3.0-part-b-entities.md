# Timerify 1.3.0 Part B (entity names, #46) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On a device that holds more than one timer, every entity of each timer names its target in brackets ("Relay Run for (Channel 1)"). Adding or deleting a timer renames its siblings at once (#46).

**Architecture:**
- **At load.** `TargetController` decides once per load whether its device holds more than one timer. If it does, it keeps the target's short name as `target_label`. `TimerifyEntity.__init__` then picks the translation key `<key>_with_target` and adds the placeholder `target`. Entity ids come from the English name the first time an entity is registered. So existing entities keep their ids, and a new second timer gets readable ones.
- **On a change of the count.** `Entity.name` is cached per entity object, so only a reload renames a loaded timer. One function in `__init__.py` runs after every timer set-up (success or failure) and after every removal. It reloads each loaded timer whose naming no longer matches the count.
- **The card.** The card's stub config finds a Run for by its registry `translation_key`, so it learns the new key.

**Tech Stack:** Python 3.14, Home Assistant 2026.10.4, pytest with freezegun, TypeScript and Lit for the card, vitest.

**Research:** `.superpowers/research-1.3.0-engine.md`, section "#46" (HA facts, the prototype table, the tests). Read it narrowly with sed or Read ranges.

**Spec:** `docs/superpowers/specs/2026-11-03-release-1.3.0-design.md`, section "Part B: entities", plus "Release" and "Constraints". Issue: `gh issue view 46`.

## Review Focus

1. **The Voice settings entry is loaded among the timers.** `async_loaded_entries(DOMAIN)` returns it too, and it has no controller. Adding a second timer must not touch it or fail on it. Test: Task 2, `test_a_second_timer_on_a_device_leaves_the_voice_settings_alone`.
2. **A third timer on a device.** Going from 2 to 3 timers and back changes no naming, so nothing is reloaded and no entity goes unavailable. Test: Task 2, `test_a_third_timer_on_the_device_reloads_nobody`.
3. **The attribute names and the icons of a renamed entity.** The frontend finds both by `translation_key`. A `_with_target` key without Ends at's and Next command's `state_attributes`, or without its icon, shows raw attribute keys and default icons. Tests: Task 1, `test_a_name_with_its_target_says_what_the_plain_name_says` and `test_every_entity_key_has_its_icon`.
4. **A new card on a dashboard whose timers are all on two-timer devices.** `getStubConfig` must still find a Run for. Test: Task 3, `it("picks a timer on a device with two timers for a new card")`.
5. **A timer that fails to load.** For example, its stored file is invalid. It still counts, so adding it still renames its sibling at once. Test: Task 2, `test_a_timer_that_fails_to_load_still_renames_its_sibling`.

- Produces, in `target.py`:

- Produces, elsewhere:
  - `TargetController.target_label: str | None`. It is `target_label(...)` when `shares_its_device(hass, target, timers_by_device(hass))`, and None otherwise. It is fixed for the load; the docstring says so.

With a `target_label`, it sets `_attr_translation_key = f"{description.translation_key}_with_target"` and `_attr_translation_placeholders = {**placeholders, "target": label}`. Without one, it sets the placeholders only when `placeholders` is given. `IntervalSwitch` passes `placeholders={"interval": subentry.title}` instead of setting the attribute itself.

  - It computes `timers_by_device(hass, removed=entry_id if removed else None)` once.

  - It covers every loaded timer, not only those on one device. So a target that moves off a device also updates the timer it left there.
- The calls:
  - `async_setup_entry`, for a timer only, in a `finally` around `_async_setup_timer`. So a timer that fails to load still renames its sibling, as it counts.
  - `async_remove_entry`, for a timer, after the stores are removed, with `removed=True`.
  - A moved target, a target that gains a device and a restored target already reload their timer (`_follow_target`, `_follow_target_gaining_a_device`, `_follow_target_restored`), so they reach the check through the set-up.

# Timerify Phase 5 — Dashboard Card Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One custom card, `timerify-card`, shipped inside the integration and loaded on every dashboard without any setup, shows a Timerify timer in a pill or a round layout (progress fill or ring, icon, name, time left counted down in the browser, end time, optional "+N" chip) and opens on tap a pop-up with duration presets, ±, stop, the interval switches, the pending commands with cancel and, for an admin, a link to the timer's settings; a long press on the round layout starts or stops the timer; a visual editor configures it — everything through Timerify's entities and services.

**Architecture:** The card is a Lit element in TypeScript (`card/`), bundled by esbuild into one committed ES module, `custom_components/timerify/frontend/timerify-card.js`, which `async_setup` serves as a static path and adds to every dashboard with `frontend.add_extra_js_url` (C1, C2). The card is configured with the timer's "Run for" number and asks Timerify once, with the read-only websocket command `timerify/timer`, for the rest: entry id, target, mode, sibling entities, intervals and the target's on-rule (C3). From then on it renders only from `hass.states` (the "Ends at" timestamp and its new `started_at` attribute, C4; the "Next command" attribute `commands`; the target; the interval switches) and acts only through `number.set_value`, `timerify.add_time`, `timerify.run`, `timerify.cancel_command` and `switch.turn_on/turn_off` (spec §2: no card-only behaviour). Strings come from `translations/<lang>.json` `common` with `hass.loadBackendTranslation("common", "timerify")` (C5); numbers, durations and clock times from `Intl` in `hass.locale`. The pop-up is a native `<dialog>` in the card's shadow DOM (C6), proved in a real Home Assistant by the E2E harness before any pop-up content is built. Each task is a vertical slice that leaves every check green.

**Tech Stack:** Python 3.14, Home Assistant 2026.10.4 (`homeassistant.components.http.StaticPathConfig` / `hass.http.async_register_static_paths`, `homeassistant.components.frontend.add_extra_js_url`, `homeassistant.components.websocket_api` `websocket_command`/`async_register_command`/`ERR_NOT_FOUND`, `helpers.entity_registry`), pytest-homeassistant-custom-component 0.13.375 (`hass_ws_client`, `hass_read_only_access_token`, `hass_client_no_auth`, `freezer`, `async_fire_time_changed`); Node 26.12.1 / npm 11.20.0; lit 3.3.3, esbuild 0.28.2, typescript 6.0.3, vitest 5.0.5, happy-dom 21.0.4, @playwright/test 1.64.1 (Chromium 1248, cached), @types/node 26.6.5; Docker (HA 2026.10.4 container, hassfest).

## Review Focus

1. **Home Assistant restarts, or the connection drops, while the card is open:** the countdown carries on to the same end, the card asks for its timer again when the connection or the number comes back (a lookup refused while Timerify is still starting is not final), and no error card is left behind (Task 3 `asks again when the timer comes back after a restart`, `asks again when the connection returns`; Task 5 E2E `keeps counting to the same end across a restart`).
2. **The card's number was renamed, or its timer deleted:** a translated warning names the entity the card is configured with (instead of a blank or a crashed card), and the card recovers on its own when the entity comes back (Task 2 `test_renamed_number_is_found_under_its_new_id`; Task 3 `names the missing entity`, `recovers when the number appears again`).
3. **The browser's clock is ahead of or behind the server's:** the time left never goes below 0:00, the fill stays within empty and full, the end time shown is the server's, and every action still goes to the server (Task 5 `is not fooled by a clock that runs ahead or behind`).
4. **A target on no device, and two timers on one device:** the card finds its own siblings from Timerify, never by device, and acts on its own timer only (Task 2 `test_target_without_a_device_is_found`, `test_two_timers_on_one_device_are_told_apart`; Task 3 `uses the entities Timerify names, not the device's`).
5. **Russian, with counts that need plural forms:** every label comes from `ru.json` or from `Intl` in Russian, no English unit word is appended to a number, and 1, 2, 5 and 21 minutes read as Russian formats them (Task 5 `formats the chip in the user's language`; Task 7 `labels presets in Russian through Intl`; Task 7 E2E `speaks Russian`).

**Interfaces:**
- Produces in `core.py`: `Snapshot.started_at: datetime | None = None` — "When the current countdown began (UTC); None while idle, while running without a countdown, and for a countdown stored before 0.5.0." The rule (C4), kept by `_set_end` as the only writer of `end` and `started_at`:

  | Writer | `started_at` |
  |---|---|
  | `set_duration`, `add` on an idle timer, strict `run_open` on a target that is off, R4 | `now` |
  | `_run_command` that sets a countdown | `command.at` (P3: the same as setting it at T, also when folded late) |
  | `_start_window` that sets the end | `window.start` |
  | `add` on a running timer (either sign), `_realign` (S2), `run_open` on a target wanted running | kept |
  | every `end = None` (stop, expiry, R3, loose open run) | `None` |

- Produces in `store.py`: `STORAGE_VERSION = 4`; `_payload` writes `"started_at"` (ISO UTC or `None`); migration from 1, 2 and 3 adds `"started_at": None`; `_validated` raises `ValueError` for a `started_at` without an `end` or later than the `end`.

- Produces in `tests/helpers.py`: `payload(..., started_at: str | None = None)`.

## Plan rulings

Decision — why — cost if wrong. C1–C12 are followed as written; these decide what they leave open.

- **The card's sources live in `card/`, a self-contained npm project (its own `package.json`, lockfile and configs); the gate runs `npm --prefix card …`** — keeps Node tooling out of the Python root and out of the HACS integration folder — one more directory to know.
- **The bundle is minified with legal comments kept at the end, without a source map; served at `/timerify_frontend/timerify-card.js`; the cache key is the first 16 hex digits of the file's SHA-256** — every dashboard loads it at boot; Lit's BSD licence notice must travel with it; `/timerify` is kept free for the later sidebar page — a reviewer reads the TypeScript, not the bundle.
- **The registration (C1) is built with the bundle (Task 3), not with the websocket command; pytest proves the static path and the headless case, the smoke test and the E2E prove the frontend path; no `home-assistant-frontend` dev dependency** — the frontend cannot be set up in pytest without that 20260930.5 package and a dozen components; the index page is checked in the real container — a regression of `add_extra_js_url` alone shows only in the smoke and E2E runs.
- **`timerify/timer` also returns `target_on`, the target's on-rule from `domains.py` as data (`OnRule` replaces `DomainBehaviour.is_on`); `default_duration` is null in loose mode; there is no `runtime` key until phase 6 adds the sensor** — the card must say "on without a countdown" and decide the long press exactly as Timerify judges the target, without a copy of the domain table (spec §2); C3's "runtime when present" is never present yet — none.
- **`started_at` (C4): the time of the set, R4 or a strict bare run; a command's own time; a window's start; kept by adding, subtracting, S2 realignment and a bare run of a running target; null otherwise; a v3 file migrates to null and its countdown shows a full fill; a beginning later than the end is a corrupt file** — the fill must be right after a late fold or a restart (P3, §5.7); an upgrade must not invent a beginning — a countdown running during the upgrade has no progress until it is set again.
- **The fill is the share of the countdown that is left (full at the start, empty at the end), clamped to 0..1; time left is `M:SS`/`H:MM:SS` rounded up, as Home Assistant's timer card** — matches C4's "open run full, idle empty" and is plural-free in every language — none.
- **Card strings are typed by the keys of `en.json` `common`; that English is bundled and used only before the strings arrive and where no `hass` exists (config errors, the picker entry, the editor's option labels); otherwise `hass.localize` after `loadBackendTranslation("common", "timerify")`** — a misspelt key fails `tsc`; `setConfig` runs before `hass` — the English text is built into the bundle, rebuilt with every change of `en.json` (`build:check` catches a stale one).
- **The lookup is asked again on a new configured entity, a new `hass.entities`, `hass.connected` turning true and the number's state becoming available; a `not_found` shows a warning, any other failure shows the card without a time until the next trigger** — after a restart the frontend reconnects before Timerify is loaded, and no event other than the number's own state says it is back — a lookup that fails while the number is available and nothing changes waits for the next trigger.
- **Presets default to 15, 30, 45, 60 and 120 minutes and accept digit strings (the editor's `select` writes strings); ± steps 5 minutes and is not configurable; `−` is offered only while counting; the chip is ignored by the round layout** — the owner's 45 minutes and the common lengths; C9 lists no step field — a user who wants another step uses a preset.
- **A hold fires on release after at least 500 ms, as Home Assistant's own action handler; a moved-off or cancelled pointer aborts; Enter and Space are a tap; the context menu is suppressed while a hold is possible; the pill has no hold, so a long press there is a tap; `data-held` marks a hold in progress (the ring pulses)** — the frontend's timing and feel — keyboard users start and stop through the pop-up.
- **The pop-up closes on Escape, on its close button and on a click on the backdrop; the browser's Back is not intercepted (Chromium on Android closes a modal dialog by itself, unverified in the companion apps); a refused action is reported by Home Assistant's own toast (`notifyOnError`), and the card catches the rejection and stays open** — no history handling that HA's internals own — Back on iOS leaves the view.
- **`ha-card`, `ha-icon` and `ha-state-icon` are the only frontend elements rendered; nothing waits for their definition** — the icon logic of every domain and the theme's card frame exist nowhere else; they are defined when a card connects (research §1) — if one is renamed, the card loses its frame or icon, not its function.
- **Clock times: the same local day shows the time, the next six days the short weekday and time, later ones the date and time; they honour `locale.time_zone` ("server" is `hass.config.time_zone`) and `time_format`** — a timer ends at most a day ahead and a command at most seven — none.
- **A new `hass` renders the card only when one of its own entities' state objects, the locale, the language, the user, the connection or the registry changed** — the setter runs on every state change of the home (research §2) — none.
- **The E2E harness is `scripts/harness/hass.py` (moved from the smoke script, parameterised by project, port and config directory), driven for the E2E by `python -m scripts.e2e.hass up|restart|down`, which Playwright's global setup and teardown call; the smoke test now runs as `uv run python -m scripts.smoke.run`** — one onboarding and compose path; smoke (18123) and E2E (18124) can run side by side — the smoke command changes.

# Timerify 1.1.1: two of the owner's decisions

Two changes the owner decided on 2026-11-03, after 1.1.0 was released. Each is a GitHub issue
with the owner's words: #57 and #58. Research with file and line references:
`.superpowers/research-1.1.1.md` (git-ignored, on the owner's machine).

## #57: an hour written with a leading zero is the morning

The owner's rule, for a clock time said or typed to Assist, in English and Russian:

- "07", "07:30": the hour on the 24-hour clock, 07:00 or 07:30, today or tomorrow, whichever
  comes first.
- "07 pm", "07:30 pm" (and "07 in the evening", Russian "v 07 vechera"): the evening. A part
  of the day or am/pm wins over the zero, as it already does.
- "7", "7:30", "seven": unchanged from 1.1.0, the nearer of 07:00 and 19:00 ahead.

Choices made here (the owner did not say; recorded in RULINGS.md):

- "Written with a leading zero" means the text the sentence matched for the hour begins with
  "0" and has more than one character. hassil keeps that text (the slot's `text`; research
  section 2). "00:30" is already the 24-hour clock and stays so. An hour said in words has no
  zero and keeps the nearer-of-two rule.
- The sentences do not change. The difference is read in `ClockCommandHandler` from the
  slot's text, the only place that applies the nearer-of-two rule (`clock_moment`).

## #58: a turn-on inside an open schedule window runs to the window's end

The owner's rule (the details in the issue were approved by the owner):

- Strict mode: the run ends at the later of the latest end of the open windows and the end of
  the default duration.
- Loose mode: the run gets a countdown to the latest end of the open windows.
- It holds after a manual off inside the window too (schedules rule 4): the windows that a
  manual off has suppressed count as open for this.
- With overlapping windows, the end is the latest end of the open windows.

Choices made here (the owner did not say; recorded in RULINGS.md):

- **Every turn-on that names no duration follows it**, not only a turn-on by hand at the
  device: a bare "turn on the boiler" to Assist, the card's run, the `timerify.run` action and
  the Run entity without minutes, and a pending turn-on without minutes when it falls due. They
  are one kind of act today (RULINGS "R9"), and a person expects the same result from the wall
  switch and from "turn on the boiler". A turn-on that names a duration keeps it.
- **The run stays the user's** (`scheduled_by` stays None, schedules rule 3): the window only
  decides how long the run is. Editing, deleting or switching off the interval later does not
  move the run. Suppressed windows stay suppressed, so the engine's realignment is untouched.
  This is the smaller change, and it keeps rule 3 true as written: a turn-on is a change of
  yours.
- A target found on at start-up, or back from "unavailable" as on, goes through the same path
  as a turn-on from outside, as it does today (RULINGS.md, the start-up report).
- In Loose mode the new countdown is a countdown like any other: "Ends at" shows it, and the
  "Countdown started" trigger and `timerify_countdown_started` fire.
- No stored field changes, so there is no storage migration.

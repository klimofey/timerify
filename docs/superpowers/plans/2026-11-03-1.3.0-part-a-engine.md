# Timerify 1.3.0 Part A (engine) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A command is carried out at the moment it was given, not when it gets the timer's lock (#42). Timerify's events carry the context of the call, button, sentence or switch that caused them, and a fresh one when time caused them (#47).

**Architecture:**
- **The moment (#42).** A command, a report of the target and an alarm each read the clock as their first line, before they wait for the lock. They hand that moment to the core, which already takes `now` everywhere. One loop thread and the first-in, first-out `asyncio.Lock` keep the moments in queue order. The start-up catch-up of a command folds to its moment too. An item due between that moment and the real time stays armed, and its alarm (armed in the past) folds it after the command.
- **The context (#47).** The controller's public methods take `context`. It travels with the change through `_command`, the fold helpers and `_execute` to `_announce`, which passes it to `hass.bus.async_fire`. Announcements that time caused are fired with no context, whatever the batch.

## Review Focus

1. **A spoken "turn off the boiler in 20 seconds" that waits 25 seconds behind a slow call.** With the delay counted from the moment given, the end it sets has passed by the time the answer is built. `timer_slots` then says `off` with no `ends_at`, and the answer template `timer_later` renders "Boiler turns off at ." (measured on the prototype). A person expects the boiler off at once and an answer naming the end. 2. **A pending command that falls due while a later command waits.** A pending "off" at 07:00:30, and "Run for 10" given at 07:00:20 behind a slow call. The "off" falls due after the moment given, so it comes after the command and wins: the device ends off, as with no slow call. Test: Task 1, `test_a_pending_off_due_while_a_command_waits_comes_after_it`.
3. **Add time given before a limit and carried out after it.** The minutes are added to the limit (the 1.2.0 rule). A person expects a countdown to the limit plus the minutes, with no `limit` end and no turn-off. Test: Task 1, `test_add_time_given_before_a_limit_and_run_after_it_adds_to_the_limit`.
4. **One call to two timers.** `timerify.run` with both Run for entities as its target. Each timer's "Countdown started" carries the call's context. Test: Task 2, `test_one_call_to_two_timers_gives_both_starts_its_context`.
5. **A call while Home Assistant starts.** The catch-up of the call folds a countdown that ended while Home Assistant was down. That `expired` is time's doing and is fresh, and the start that the call makes carries the call. Test: Task 2, `test_a_call_while_starting_gives_its_context_to_its_own_start_only`.
